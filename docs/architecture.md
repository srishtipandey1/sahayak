# Architecture

## Pipeline
bbox + event date
  -> ingest      (Sentinel-1 pair, Sentinel-2 scenes + cloud mask, DEM, OSM snapshot)
  -> terrain     (slope, HAND, valley mask from DEM)
  -> flood       (Sentinel-1 change detection + terrain masks -> water/disturbance mask + confidence)
  -> optical     (Sentinel-2 reflectance change + terrain masks -> optical change classes)
  -> ml          (segmentation model refines or replaces the baseline mask)
  -> damage      (OSM buildings, roads, bridges intersected with the mask)
  -> access      (road graph, remove hit edges, route to nearest town/hospital, list cut-off settlements)
  -> flowpath    (DEM flow tracing from an upstream point, settlements along the path)
  -> facts.json  (single source of truth for every reported number)
  -> copilot     (answers and reports from facts.json only; EN / HI / NE)
  -> report + api + dashboard

## Modules
ingest: download and cache inputs, record provenance. flood: baseline mapping. ml: dataset, training, inference, evaluation. damage: exposure analysis. access: network analysis. flowpath: bonus tracing. copilot: grounded language layer and verifier. report: one-page PDF. api: FastAPI serving layers and facts to the dashboard. provenance: run manifest and rule guards.

OSM ingestion uses a provider interface selected by `OSM_PROVIDER`: Overpass (default) makes date-pinned, sequential tile queries; ohsome v2 uses its authenticated extraction API. Overpass requests metadata and geometry, verifies every returned element timestamp against the selected snapshot, stores only layer-whitelisted columns plus the complete tags as JSON, and publishes its GeoPackage atomically.

Sentinel-1 ingestion authenticates with Copernicus Data Space OAuth, searches the Catalog for IW GRD slices, groups slices into data-takes, and selects only pre/post acquisitions sharing the same positive relative orbit and pass direction. Instrument mode, polarisation, platform, and acquisition time use the Catalog properties when available, with the Sentinel-1 item ID as a checked fallback; unsupported or malformed items are excluded individually and recorded in `selection.json`. If a Catalog relative orbit is missing or invalid, ingestion looks for a matching platform and acquisition time in the main Copernicus Data Space STAC and caches that lookup. Acquisitions without valid track metadata are excluded and recorded in `selection.json`. Process API output is requested in windows aligned to the common UTM grid and written as float32 Cloud Optimized GeoTIFFs. The implementation uses the documented 2500-pixel maximum per output dimension; grids within that limit use one request, and larger grids are tiled.

Sentinel-2 ingestion searches `sentinel-2-l2a` from 45 days before to 70 days after the event date. It deduplicates same-date Catalog items by the lowest tile-level `eo:cloud_cover`, screens at most six pre-event and eight post-event candidates with cached 60 m SCL requests, and records candidate fractions and selection reasons. The local bbox clear fraction uses SCL classes 4-7; class 2 (dark area), 3 (cloud shadow), 8-10 (cloud/cirrus), 11 (snow/ice), and 0-1 (no data/defective) remain separately reported. It selects the latest pre-event scene with at least 50% clear pixels and the earliest post-event scene with at least 80%, falling back to the best clear-fraction candidate when necessary. The chosen images are fetched once each at 10 m on the shared grid as eight-band float32 COGs. The Process API input requests BOA reflectance for B02/B03/B04/B08/B11/B12 and DN for SCL/dataMask. COG nodata is retained in the source profile and COG-copy creation omits unsupported `nodata`/`photometric` options; Rasterio/GDAL can still warn when opening the service-returned multi-band Process TIFF, whose source photometric-channel metadata is inconsistent with its sample count. The optical quicklooks use one fixed pre-scene 2nd-98th percentile stretch and show SCL cloud/shadow/snow, OSM roads/settlements, and the stream overlay when a flood stream network already exists.
Sentinel-2 ingestion also selects an earlier `s2_pre_2.tif` placebo scene, preferring the best evaluated pre-event scene with at least 50% clear pixels and at least ten days between it and the selected baseline. If that constraint cannot be met, the best distinct earlier evaluated scene is used and explicitly marked as a fallback; if none exists, the selected baseline is reused and flagged. It additionally screens post-event acquisitions at least 14 days after the selected post scene and selects the clearest with at least 90% local SCL clear pixels as `s2_post_2.tif`; if none qualifies, ingestion stops with an explicit error.

Flood mapping uses the Sentinel-1 VV/VH, local-incidence-angle, shadow-mask, and data-mask bands by description. The Sentinel Hub Sentinel-1 GRD documentation defines `localIncidenceAngle` as the angle in degrees for each output pixel (available with orthorectification), `dataMask` as the data/nodata mask (0 no data, 1 data), and `shadowMask` as true for pixels in or near radar shadow: the nearest GRD source pixel is no more than one GRD pixel from a pixel with normalized `scatteringArea < 0.05` (0 likely not in shadow; 1 likely in/near shadow). This stage excludes positive shadow-mask values. These documented mask flags do not establish a separate layover flag.

The flood stage applies a masked Lee filter to linear power, converts filtered VV/VH to dB, and uses the three pre-event images for the per-pixel baseline. Terrain conditioning, D8 flow direction, accumulation, and HAND run on a configurable 30 m working grid: the GLO-30 DEM is averaged from the 10 m common grid, and HAND is bilinearly resampled while streams are nearest-neighbour resampled back to the 10 m output grid. PySheds computes HAND from the same conditioned DEM used for flow direction. Stream cells use an upstream-area threshold from `configs/flood.toml`. The DEM is Copernicus GLO-30; resampling does not add terrain detail, so effective terrain resolution remains about 30 m. HAND negative-value QC and the fraction of stream cells below the selected pre-event VV water threshold are recorded in `facts.json`. Flood and disturbed-surface thresholds, cleanup, confidence, and HAND sensitivity values are also recorded there; confidence is a documented heuristic, not a calibrated probability. Outputs are written under `runs/<run_id>/flood/`.

The `flood-diagnose` command writes sequential new-water, disturbed-surface, and permanent-water candidate counts to `flood/diagnostics.json`. It reports uncapped and clamped Otsu values, valid-pixel backscatter/change/z-score percentiles, stream and HAND-corridor validity, exclusive invalid-mask reason shares by image and combined, main-river incidence-angle summaries, and a pre-event null-pair placebo using the oldest two selected baseline scenes and the newest pre-event scene as the pseudo-post. The placebo's mapped classes are false alarms by construction, not ground truth. Its robust noise estimates are `1.4826 * MAD`, overall and in local-slope bands. Permanent water is restricted to HAND at most 15 m, slope at most 10 degrees, and the configured minimum connected-component area; baseline-dark pixels not retained as water are class 4 `dark_low_confidence`. Flood facts store source files, scene dates, and thresholds once in the section's `provenance`; individual measurements reference that provenance.

The `optical` command uses the selected pre-event scene as baseline and selected post-event scene for change. It evaluates two placebos: the earlier `s2_pre_2.tif`/`s2_pre.tif` pair and the later `s2_post.tif`/`s2_post_2.tif` pair; the latter is primary for reliability only when its valid fraction is at least 70%. It requires both dates to have SCL 4-7, a positive data mask, and finite reflectance in [0, 1.5], then dilates invalid pixels by two cells for classes 1-3. Post-event bands are normalized to pre-event using a median-ratio scale and median offset fitted per band to HAND > 100 m, slope <= 35 degree stable pixels after excluding the 2% tails of each band's change distribution. The fixed scour, new-water, and existing-channel/bare rules and cleanup settings are in `configs/optical.toml`; connected detections are opened, area-filtered, and restricted to 150 m of streams. `bright_recovered` is a separate, undilated SCL 8-11 heuristic with elevation, HAND, stream, normalized B04 change, NDVI, and blue-reflectance gates followed by component-area, corridor-fraction, and proximity checks. It is capped at 0.5 confidence using the existing optical confidence score before capping: 0.4 normalized absolute dNDVI, 0.25 normalized distance from invalid pixels, and 0.2 normalized absolute null-MAD z-score (including the slope term). Hazard footprints are reported as strict (class 1 with confidence >= 0.6), default (classes 1, 2, and 4), and lenient (default plus a 30 m buffer). Bright recovery is not a validated sediment classifier. A control with bbox or corridor clear fraction below 70% makes reliability `unverified`. The placebos are false-alarm checks, not ground truth. Confidence is a heuristic score, not a calibrated probability. Sensitivity results, class areas, null rates, normalization coefficients, and radar corroboration are measurements and are not validation of map correctness.

`ingest-network --run-id ... --bbox ...` reuses the run's verified pre-event OSM snapshot with the date-pinned Overpass provider and request cache. It reports the logical request estimate before extraction, requests one 0.1-degree tile at a time with pacing and retries, checks element timestamps, and writes roads, bridges, health facilities, and settlements to `network_osm_pre_event.gpkg` in the common grid CRS. The `damage` command uses the run focus bbox and writes `exposure.gpkg` plus the three scenario measurements in `facts.json`. Buildings intersecting the footprint count as inside; buildings within 30 m but not intersecting count as near; roads contribute intersected length by highway class; bridges count within 20 m; settlements count when within 100 m of a footprint or within 300 m of a hit building.

The `access` command routes wide-area settlements to OSM health facilities and town/city targets before and after removing hazard-hit edges. `configs/access.toml` documents assumed road speeds, 3 m endpoint snapping, 500 m settlement and target snapping, and the degraded threshold (at least 50% or 5 km farther). These are scenario assumptions, not measured travel times or confirmed road closures. Roads are noded at crossings; each affected edge is removed if it intersects a footprint, with bridges also removed within 20 m. Outputs are `settlement_access.gpkg`, `blocked_edges.gpkg`, and `access_map.png`; `facts.json` stores class counts, blockers, and the cut-off set common to all three scenarios. Unassessable settlements remain counted so missing network coverage is visible. Population is never estimated or reported. Hazard footprints are detections, not ground truth.

`doctor --list-s2` is a read-only Sentinel Hub Catalog search for Sentinel-2 L2A item metadata. It reports Catalog acquisition date, tile identifier when present in item metadata or ID, relative orbit when present, and `eo:cloud_cover` as a tile-level percentage when supplied. It makes no Process API request and downloads no pixels.

## Formats
Rasters: Cloud Optimized GeoTIFF in a projected UTM CRS chosen from the bbox. Vectors: GeoPackage. Facts: JSON. Dashboard layers: GeoJSON or tiles derived from these.

## Run folder layout
runs/<run_id>/manifest.json, inputs/, masks/, vectors/, facts.json, report/, logs/

## facts.json principles
Every value carries its unit, the module that produced it, and the input scenes it depends on. No number appears in a report unless it is in facts.json.
